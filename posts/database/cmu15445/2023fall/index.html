环境配置

mac 下没什么好说的，但是在 linux 下着实费了点功夫，bits/c++-config.h 这个在lsp的插件上总是显示该文件无法找到，解决办法如下：

  • 首先，使用 locate c++-config.h 找到该头文件所在的目录，我的 Fedora 42 环境下是/usr/include/c++/15/x86_64-redhat-linux/bits
  • 在 cmake 的时候，在 Debug 模式下设置变量 -DCMAKE_CXX_FLAGS_DEBUG=-I/usr/include/c++/15/x86_64-redhat-linux 提供一个我的环境下使用的命令:
#linux - fedora 42
cmake -DCMAKE_EXPORT_COMPILE_COMMANDS:BOOL=TRUE -DCMAKE_BUILD_TYPE:STRING=Debug   -DCMAKE_CXX_FLAGS_DEBUG=-Wno-deprecated-literal-operator\ -I/usr/include/c++/15/x86_64-redhat-linux    -DCMAKE_C_COMPILER:FILEPATH=/usr/bin/clang  -DCMAKE_CXX_COMPILER:FILEPATH=/usr/bin/clang++  ..
#mac
cmake -DCMAKE_EXPORT_COMPILE_COMMANDS:BOOL=TRUE -DCMAKE_BUILD_TYPE:STRING=Debug   ..

即可正常使用。

唯一不爽的是，clang-tidy 检查这个本地没有问题，一提交总是会出错，虽然很尴尬，但是可以忍受，所以也就没有去查找原因。

project #2：Hash Index

这个 project 主要是实现 Extendible Hash 算法，document 上的描述很少，所以翻了不少资料，下面描述其实现逻辑。

Extendible Hash 是一种动态可扩展哈希数据结构，常用在数据库的实现中。它有几个重要的概念：

  • Bucket，桶，用来存储键值对，Bucket 中的 K/V 的个数是固定的。
  • Directory，目录，用来存放指向 Bucket 的指针，可以动态生长，是一个线性的数组。
  • Global Depth，假设其值为$n$，则该 Directory 的大小：$2^{n}$，且通过 hash(key) 二进制的低 $n$ 位来进行索引。例如，hash(key) 的二进制为111且 $n=2$, 则 Bucket 就是 $Directory[(11)_{2}]$
  • Local Depth，每个 Bucket 都有各自的 Local Depth，且必定小于或者等于 Global Depth。假设其值为 $n$，在当前 Bucket 下的 hash(key)的二进制 低 $n$ 位都是相同的。

如下图就是一个 Global Depth 和 Local Depth 都为1, Bucket size 为2 的 Extendible Hash table：

对于某个 Bucket，当 Local Depth 和 Global Depth 相等，通过 Directory 有且只有唯一的下标可以索引到该 Bucket；当 Local Depth 小于 Global Depth时，通过 Directory 必定有多个 下标可以索引到该 Bucket，下标的个数计算公式：$2^{Global_Depth - Local_Depth}$。

以 Global Depth 和 Local Depth 都为1, Bucket size 为2 为例来分析插入的流程。 插入 $0$（为了方便描述，key为数字，hash后的值为其本身）, 根据上述对 Extendible Hash 的描述，此时 Global Depth 为 1, 所以取 0 的二进制的低1位也就是0来获取 Bucket：$Directory[0]$，然后把其存储到 Bucke中。依次类推插入1,2,3 后如下图：

Directory Growing

插入 4，其二进制为 100，根据规则应该放入到 上图中的 Bucket1 中，但是该 Bucket 已经满了，需要进行分裂，有如下步骤：

  • 当前桶的 Local Depth 增 1, 然后分裂出新桶，新桶的 Local Depth 等于 当前桶的 Local Depth。
  • 因为当前桶的 Local Depth 增1后，大于 Global Depth， 此时 Global Depth 需要 增1，这意味着需要对 Directory 进行扩容，扩容后的大小是当前容量的2倍。
  • 记住一个前提：** Bucket 下的 key 哈希后的值的二进制低 $Local Depth$ 位都是相同的**。需要对被分裂的桶中的键值对和新插入的4在这两个桶中进行重新分配，然后以 key 哈希后的值的二进制低 $Local Depth$ 位为下标，更新 Directory 中指向各个Bucket的指针。

从上图可以看到，Bucket2 的 Local Depth 的值为1,所以指向该 Bucket 的指针有 $2^{2-1}$ 个，也就是2个。 按照上面的逻辑，在插入8，结果如下： 下面，让我们来插入 9， 其二进制为 1001，这里是要插入到 Bucket2 中， Bucket2 的 Local Depth 为1 且是个满桶，所以需要分裂，其 Local Depth的值加 1 后仍然小于 Global Depth，所以 Directory不会扩容，但是指向 Bucket2 的指针的条数会减半，具体如下下图所示。

TEST(ExtendibleHTableTest, RemoveTest5) {
  auto disk_mgr = std::make_unique<DiskManagerUnlimitedMemory>();
  auto bpm = std::make_unique<BufferPoolManager>(50, disk_mgr.get());

  DiskExtendibleHashTable<int, int, IntComparator> ht("blah", bpm.get(), IntComparator(), HashFunction<int>(), 2, 3, 2);
  ht.VerifyIntegrity();
  ht.Insert(4, 4);
  ht.PrintHT();
  ht.Insert(5, 5);
  ht.PrintHT();
  ht.Insert(6, 6);
  ht.PrintHT();
  ht.Insert(14, 14);
  ht.VerifyIntegrity();
  ht.PrintHT();

  std::cout << "remove 5" << std::endl;
  ht.Remove(5);
  ht.PrintHT();

  std::cout << "remove 14" << std::endl;
  ht.Remove(14);
  ht.PrintHT();

  std::cout << "remove 4" << std::endl;
  ht.Remove(4);
  ht.PrintHT();
}

project #4：concurrency control
