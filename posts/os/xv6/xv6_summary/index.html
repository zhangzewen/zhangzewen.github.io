xv6 总结

Created: Aug 5, 2025 · 15 min read

本篇文章是对学习 xv6 系统的理解和总结，权当笔记，以便日后翻阅，如果阅读起来很跳跃和不连贯，请见谅。

内存管理

xv6 page table

上图是 RISC-V 多种虚拟内存布局中的一种 — Sv39。

通常，第一级 page table entry（上图的L2）指向第二级 page table，第二级 page table entry（上图的L1）指向第三级 page table，第三级 page table entry（上图的L0）指向的是实际的物理内存，将连续的且对齐的 4KB 虚拟内存映射到连续的且对齐的 4KB 物理内存（注意上面的虚拟地址的 offset， $1«12 = 4096$，所以对一个实际的物理地址左右移动不超过 12 位，都可以复原到原本的物理地址）。

和第三级 page table entry 的功能相似，如果第二级 page table entry 是叶子节点，则它指向的是 2MB 的物理内存。还需要知道的是如果第一级 page table entry 是叶子节点，则它指向的是 1GB 的物理内存。

一个 page table 的大小是 4KB， 一个 page table entry 的大小是 8 bytes，所以 Sv39 可以的表达 512GB 的内存空间。

xv6 为每个进程维护一个page table，描述每个进程的用户地址空间，再加上一个单独的页表（全局 kernel_pagetable）来描述内核的地址空间映射。内核通过预设地址空间的布局，以便通过虚拟地址获得对物理内存和各种硬件资源的访问。

xv6 内核内存布局

如下是内核的page table 映射布局，其逻辑实现在 kernel/vm.c 下的 kvminit，特别需要注意的是proc_mapstacks 和 procinit，他给每个进程都分配了内核栈且映射信息是保存在内核 page table上的，下图的 Guard page 其实就是没有做映射的虚拟地址段。然后调用kvminithart 把 内核 page table 的物理地址写入到寄存器 satp中。

xv6 用户进程内存布局

每个进程都有自己的page table，当xv6在进程之间切换时，它也切换了page table，用户进程的page table 的虚拟地址最大为 MAXVA，即可以达高达 256GB 的内存空间，这个值定义在kernel/riscv.h中。

下面来拆解这张图是怎么实现的。

在交互环境（执行 make qemu 进入）下执行ctrl + p 可以看到类似ps命令的结果：

$
1 sleep  init
2 sleep  sh

第一个用户进程就是init，它是通过 kernel/main.c 下的 userinit 初始化和拉起来的：

void
userinit(void)
{
  struct proc *p;

  p = allocproc();
  initproc = p;
  
  // allocate one user page and copy initcode's instructions
  // and data into it.
  uvmfirst(p->pagetable, initcode, sizeof(initcode));
  p->sz = PGSIZE;

  // prepare for the very first "return" from kernel to user.
  p->trapframe->epc = 0;      // user program counter
  p->trapframe->sp = PGSIZE;  // user stack pointer

  safestrcpy(p->name, "initcode", sizeof(p->name));
  p->cwd = namei("/");

  p->state = RUNNABLE;

  release(&p->lock);
}

从上面的代码可以看到 initcode 的流程如下：

  • 使用 allocproc 分配进程，在这里会给每个进程分配一个page table，并调用 proc_pagetable 设置初始的映射，这里需要注意 TRAMPOLINE 的映射信息，这个是实现用户态和内核态平滑切换的关键。
  • 把 initcode.S 拷贝到分配到的 页 中，并把该页映射到虚拟地址0x0，这段逻辑在uvmfirst中实现。
  • 设置栈帧，并修改为状态为RUNNABLE

至此已经完成上图的头尾两端的映射逻辑实现。如下是initcode.S 的汇编代码，只需要知道是使用系统调用 exec 来调用 init.c 即可：

如下是 exec 的代码： exec 执行流程如下：

  • 创建新的page table，并设置其虚拟地址顶部的映射关系，完成上图的顶端部分。
  • 装载可执行文件到内存中，以虚拟地址0x0开始，注意如下代码中的变量sz，这就完成了上图的底端部分。
  • 然后申请两个页来做用户态的栈空间，但是又清除一个页（用户栈下方）的映射作为Guard page，即用户栈的大小是一个页，用户栈是向下增长的，生长到 Guard page 会产生 exception。
  • 拷贝参数到用户栈，此步骤和上一步完成上图的中间部分。
  • 替换page table，以及设置寄存器

int
exec(char *path, char **argv)
{
  char *s, *last;
  int i, off;
  uint64 argc, sz = 0, sp, ustack[MAXARG], stackbase;
  struct elfhdr elf;
  struct inode *ip;
  struct proghdr ph;
  pagetable_t pagetable = 0, oldpagetable;
  struct proc *p = myproc();

  begin_op();

  if((ip = namei(path)) == 0){
    end_op();
    return -1;
  }
  ilock(ip);

  // Check ELF header
  if(readi(ip, 0, (uint64)&elf, 0, sizeof(elf)) != sizeof(elf))
    goto bad;

  if(elf.magic != ELF_MAGIC)
    goto bad;
  // 可以理解为其复制了调用exec的进程的头部虚拟地址映射关系
  if((pagetable = proc_pagetable(p)) == 0)
    goto bad;

  // Load program into memory.
  for(i=0, off=elf.phoff; i<elf.phnum; i++, off+=sizeof(ph)){
    if(readi(ip, 0, (uint64)&ph, off, sizeof(ph)) != sizeof(ph))
      goto bad;
    if(ph.type != ELF_PROG_LOAD)
      continue;
    if(ph.memsz < ph.filesz)
      goto bad;
    if(ph.vaddr + ph.memsz < ph.vaddr)
      goto bad;
    if(ph.vaddr % PGSIZE != 0)
      goto bad;
    uint64 sz1;
    if((sz1 = uvmalloc(pagetable, sz, ph.vaddr + ph.memsz, flags2perm(ph.flags))) == 0)
      goto bad;
    sz = sz1;
    if(loadseg(pagetable, ph.vaddr, ip, ph.off, ph.filesz) < 0)
      goto bad;
  }
  iunlockput(ip);
  end_op();
  ip = 0;

  p = myproc();
  uint64 oldsz = p->sz;

  // Allocate some pages at the next page boundary.
  // Make the first inaccessible as a stack guard.
  // Use the rest as the user stack.
  sz = PGROUNDUP(sz);
  uint64 sz1;
  // 申请两个页并做映射
  if((sz1 = uvmalloc(pagetable, sz, sz + (USERSTACK+1)*PGSIZE, PTE_W)) == 0)
    goto bad;
  sz = sz1;
  // 清除用户栈下的页的映射，作为 Guard page
  uvmclear(pagetable, sz-(USERSTACK+1)*PGSIZE);
  // 设置栈帧
  sp = sz;
  stackbase = sp - USERSTACK*PGSIZE;

  // Push argument strings, prepare rest of stack in ustack.
  // 把内核态的参数列表拷贝到刚申请的用户态的栈中
  for(argc = 0; argv[argc]; argc++) {
    if(argc >= MAXARG)
      goto bad;
    sp -= strlen(argv[argc]) + 1;
    sp -= sp % 16; // riscv sp must be 16-byte aligned
    if(sp < stackbase)
      goto bad;
    if(copyout(pagetable, sp, argv[argc], strlen(argv[argc]) + 1) < 0)
      goto bad;
    ustack[argc] = sp;
  }
  // 休止标志位
  ustack[argc] = 0;

  // push the array of argv[] pointers.
  // 参数列表的首地址压入到栈中
  sp -= (argc+1) * sizeof(uint64);
  sp -= sp % 16;
  if(sp < stackbase)
    goto bad;
  if(copyout(pagetable, sp, (char *)ustack, (argc+1)*sizeof(uint64)) < 0)
    goto bad;

  // arguments to user main(argc, argv)
  // argc is returned via the system call return
  // value, which goes in a0.
  p->trapframe->a1 = sp;

  // Save program name for debugging.
  for(last=s=path; *s; s++)
    if(*s == '/')
      last = s+1;
  safestrcpy(p->name, last, sizeof(p->name));
    
  // Commit to the user image.
  // 替换page table
  oldpagetable = p->pagetable;
  p->pagetable = pagetable;
  // 设置进程栈的大小，其实也是heap的起始位置
  p->sz = sz;
  // 设置pc 寄存器，指向下一个要执行的指令
  p->trapframe->epc = elf.entry;  // initial program counter = main
  // 设置栈指针sp
  p->trapframe->sp = sp; // initial stack pointer
  // 释放掉旧的pagetable
  proc_freepagetable(oldpagetable, oldsz);

  return argc; // this ends up in a0, the first argument to main(argc, argv)

 bad:
  if(pagetable)
    proc_freepagetable(pagetable, sz);
  if(ip){
    iunlockput(ip);
    end_op();
  }
  return -1;
}

trap 机制

根据 xv6 book 所述，以下三种状况会导致从用户态到内核态的切换：

  • 系统调用，例如调用 write/open 等系统函数，更进一步就是调用 ecall 指令。
  • 异常，例如除以零或使用了无效的虚拟地址。
  • 设备中断，当设备发出需要处理的信号时，例如磁盘硬件完成读或写请求，该中断无论发生在用户态或者是内核态，回调函数的处理都是在内核态下处理。

这里使用 “trap” 作为以上这些情况的通用词。

RISC-V 特权级别

任何时候一个 RISC-V 硬件线程（hart）都在某个特权级别上运行，该特权级别存储在一个或多个控制和状态寄存器中。尝试执行当前权限级别不允许的操作将导致引发异常，这些异常通常会导致陷入底层执行环境。

特权名称 级别 编码 简称
User/Application 0 00 U
Supervisor 1 01 S
Reserved 2 10
Machine 3 11 M

Machine Mode（ M 模式）具有最高的特权，User Mode（用户模式，即 U 模式）和 Supervisor Mode（监督模式，即 S 模式，更常用的称呼为 内核模式）分别用于常规应用程序和操作系统使用。

控制和状态寄存器

控制和状态寄存器即 CSRs，是存储CPU中各种信息的寄存器。标准的 RISC-V ISA 保留了一个12位的编码空间，因此最多可以有 4096 个 CSR。 在这 12 位的编码空间中，其中最高两位指示寄存器是读/写（00、01或10）还是只读（11）。接下来的两位确定可以访问该寄存器的最低权限级别。 RISC-V 只分配了部分地址空间，以便在未使用的地址中添加自定义的 CSR。

mstatus/sstatus

寄存器 mstatus/sstatus 跟踪并控制 CPU 当前的运行状态（机器模式/监督模式），sstatus 继承自 mstatus：

  • MPP，指示 hart 在进入机器模式之前执行的特权级别。当执行一个 mret 指令从 trap 处理程序返回时，特权等级会被设置为 MPP 所存储的值所对应的特权级别。
  • MIE，启用或禁用机器模式下的所有中断。
  • MPIE，指示在陷入机器模式之前是否启用了中断。当陷入机器模式时，MPIE 的值设置为 MIE 的值，然后 MIE 设置为0。当执行 mret 指令时，MIE 的值设置为 MPIE 的值，然后 MPIE 设置为1。

  • SPP，指示 hart 在进入监督模式之前执行的特权级别。当执行一个 sret 指令从 trap 处理程序返回时，特权等级会被设置为 SPP 所存储的值所对应的特权级别。
  • SIE，启用或禁用监督模式下的所有中断。
  • SPIE，指示在陷入监督模式之前是否启用了中断。当陷入监督模式时，SPIE 的值设置为 SIE 的值，然后 SIE 设置为0。当执行 sret 指令时，SIE 的值设置为 SPIE 的值，然后 SPIE 设置为1。

在 kernel/start.c，在机器模式下，设置前一个特权级别为监督模式，可以类比上面的SSP， 这个是给 mret 使用，即执行 mret 时候 返回到监督模式：

  // set M Previous Privilege mode to Supervisor, for mret.
  unsigned long x = r_mstatus();
  x &= ~MSTATUS_MPP_MASK;
  x |= MSTATUS_MPP_S;
  w_mstatus(x);

stvec

内核将它的异常处理程序地址写入寄存器 stvec，RISC-V 跳转到 stvec 中的地址来处理异常，即把寄存器 stvec 的值赋值给寄存器 pc。在 xv6 中，kernelvec（kernelvec.S）负责处理发生在内核态的 trap， uservec（trampoline.S）负责发生在用户态的 trap。

sepc

当 trap 触发时，寄存器 pc 的值保存于此（因为此时 pc 被 stvec 中的值覆盖）。sret（从 trap 返回）指令将 sepc 的值复制到pc。

sscratch

寄存器 sscratch 主要用于在用户态和内核态切换时临时保存数据，特别是在 trap 处理过程中。它的核心作用是提供一个安全的临时存储空间，避免关键寄存器的值被破坏。

trap 处理流程

在 kernel/start.c 中：

  // delegate all interrupts and exceptions to supervisor mode.
  w_medeleg(0xffff);
  w_mideleg(0xffff);
  w_sie(r_sie() | SIE_SEIE | SIE_STIE | SIE_SSIE);

即当 trap 发生时候，不管处在何种特权模式下，统一都是在监督模式下处理。

总体来说，在监督模式下，当 trap 发生时候，硬件的处理流程如下：

  • 关闭中断
  • 寄存器 pc 的值赋值给寄存器 sepc。
  • 寄存器 stvec 的值赋值给寄存器 pc。
  • 设置寄存器 scause ，告知触发 trap 的原因。
  • 设置寄存器 stval，保存额外的信息，例如发生page fault 时候，保存的是虚拟地址。
  • 设置寄存器标志位 sstatus.SPP，即保存进入监督模式之前执行的特权级别。
  • 设置寄存器标志位 sstatus.SPIE，即保存进入监督模式之前中断开关情况。
  • 执行处理 trap 异常逻辑，即回调函数。
  • 处理异常完毕后调用 sret 返回：
    • 把标志位 sstatus.SPIE 的值赋值给标志位 sstatus.SIE。
    • 根据标志位 sstatus.SPP 的值来设置当前特权级别。
    • 把寄存器 sepc 的值赋值给寄存器 pc。

机器模式下 trap 的处理可以类比上述流程。

xv6 用户态触发 trap 处理流程

uservec

根据 上述 trap 的处理流程，用户态处理 trap 的回调逻辑地址是 uservec，其实现在 kernel/trampoline.S 下：

        #
        # low-level code to handle traps from user space into
        # the kernel, and returns from kernel to user.
        #
        # the kernel maps the page holding this code
        # at the same virtual address (TRAMPOLINE)
        # in user and kernel space so that it continues
        # to work when it switches page tables.
        # kernel.ld causes this code to start at 
        # a page boundary.
        #

#include "riscv.h"
#include "memlayout.h"

.section trampsec
.globl trampoline
.globl usertrap
trampoline:
.align 4
.globl uservec
uservec:    
	#
        # trap.c sets stvec to point here, so
        # traps from user space start here,
        # in supervisor mode, but with a
        # user page table.
        #

        # save user a0 in sscratch so
        # a0 can be used to get at TRAPFRAME.
        csrw sscratch, a0   # 保存 函数返回值 存储寄存器 a0 到 sscratch中

        # each process has a separate p->trapframe memory area,
        # but it's mapped to the same virtual address
        # (TRAPFRAME) in every process's user page table.
        li a0, TRAPFRAME #把 p->trapframe 的地址保存到a0中 
        
        # save the user registers in TRAPFRAME 
        # 存储各个寄存器到 p->trapframe, 即保存进程的状态
        sd ra, 40(a0)
        sd sp, 48(a0)
        sd gp, 56(a0)
        sd tp, 64(a0)
        sd t0, 72(a0)
        sd t1, 80(a0)
        sd t2, 88(a0)
        sd s0, 96(a0)
        sd s1, 104(a0)
        sd a1, 120(a0)
        sd a2, 128(a0)
        sd a3, 136(a0)
        sd a4, 144(a0)
        sd a5, 152(a0)
        sd a6, 160(a0)
        sd a7, 168(a0)
        sd s2, 176(a0)
        sd s3, 184(a0)
        sd s4, 192(a0)
        sd s5, 200(a0)
        sd s6, 208(a0)
        sd s7, 216(a0)
        sd s8, 224(a0)
        sd s9, 232(a0)
        sd s10, 240(a0)
        sd s11, 248(a0)
        sd t3, 256(a0)
        sd t4, 264(a0)
        sd t5, 272(a0)
        sd t6, 280(a0)

	# save the user a0 in p->trapframe->a0
        csrr t0, sscratch
        sd t0, 112(a0)

        # initialize kernel stack pointer, from p->trapframe->kernel_sp
        # 将 kernel栈帧的栈顶存储到寄存器sp中
        ld sp, 8(a0)

        # make tp hold the current hartid, from p->trapframe->kernel_hartid
        # 将 hartid 储存到寄存器 tp 中
        ld tp, 32(a0)

        # load the address of usertrap(), from p->trapframe->kernel_trap
        # 将 函数 usertrap() 的地址存储到寄存器 t0 中
        ld t0, 16(a0)

        # fetch the kernel page table address, from p->trapframe->kernel_satp.
        # 将 kernel 的 page table 的地址 kernel_pagetable 存储到寄存器 t1 中， 
        ld t1, 0(a0)

        # wait for any previous memory operations to complete, so that
        # they use the user page table.
        # 切换到内核的 page table
        sfence.vma zero, zero

        # install the kernel page table.
        csrw satp, t1

        # flush now-stale user entries from the TLB.
        sfence.vma zero, zero

        # jump to usertrap(), which does not return
        # jump 到函数 usertrap()
        jr t0
        # ...

根据上面的代码，uservec 的处理流程如下：

  • 用户态
    • 存储用户态函数执行状态（存储各种寄存器）。
    • 设置内核栈帧数据，获取 内核态 page table 的地址
  • 内核态
    • 从用户态 page table 切换到 内核态 page table。
    • 跳转到函数 usertrap 。
usertrap

下面来看下 usertrap 这个函数，这个函数在 kernel/trap.c 下，这个是核心部分：

void
usertrap(void)
{
  int which_dev = 0;

  if((r_sstatus() & SSTATUS_SPP) != 0)
    panic("usertrap: not from user mode");

  // send interrupts and exceptions to kerneltrap(),
  // since we're now in the kernel.
  // 把内核态的 trap 处理函数 kernelvec的地址存储到 寄存器STVEC，因为需要处理内核态发生 trap 的情形
  w_stvec((uint64)kernelvec);

  struct proc *p = myproc();
  
  // save user program counter.
  // 把寄存器 SEPC 的值存储到 p->trapfram->epc, 从上面得知是用户态时候的寄存器 pc 的值
  p->trapframe->epc = r_sepc();
  // 判断是因为啥而触发了trap 
  if(r_scause() == 8){
    // system call
    // 系统调用

    if(killed(p))
      exit(-1);

    // sepc points to the ecall instruction,
    // but we want to return to the next instruction.
    // 用户态 调用 ecall 时的下一条指令，衔接 ecall 返回后，即返回到用户态后继续执行，避免再次调用ecall造成死循环
    p->trapframe->epc += 4;

    // an interrupt will change sepc, scause, and sstatus,
    // so enable only now that we're done with those registers.
    intr_on();
    // 执行系统调用
    sysdall();
  } else if((which_dev = devintr()) != 0){ // 设备中断
    // ok
  } else { // 异常状态，杀死进程
    printf("usertrap(): unexpected scause 0x%lx pid=%d\n", r_scause(), p->pid);
    printf("            sepc=0x%lx stval=0x%lx\n", r_sepc(), r_stval());
    setkilled(p);
  }

  if(killed(p))
    exit(-1);

  // give up the CPU if this is a timer interrupt.
  if(which_dev == 2)// 时钟中断
    yield();

  usertrapret();
}

usertrap 的处理流程如下：

  • 设置寄存器 stvec 的值为内核态trap 的处理逻辑的地址，即 kernelvec，因为是用户态触发的trap，会进入到内核态的环境来处理，在这期间可能会有 trap 触发。
  • usertrap 根据 trap 触发的原因执行与之对应的处理动作：
    • ecall，执行对应的系统调用
    • 设备中断，目前来看是不做任何处理的
    • 异常，杀死进程
    • 时钟中断，执行 yield 切换进程
  • 上述处理完成后，执行 usertrapret 从处理 trap 回调逻辑中返回。
usertrapret

如下是 usertrapret 的代码：

void
usertrapret(void)
{
  struct proc *p = myproc();

  // we're about to switch the destination of traps from
  // kerneltrap() to usertrap(), so turn off interrupts until
  // we're back in user space, where usertrap() is correct.
  intr_off();

  // send syscalls, interrupts, and exceptions to uservec in trampoline.S
  // 设置寄存器STVEC ，指向 trampoline, 首尾呼应 
  uint64 trampoline_uservec = TRAMPOLINE + (uservec - trampoline);
  w_stvec(trampoline_uservec);

  // set up trapframe values that uservec will need when
  // the process next traps into the kernel.
  // 填充 p->trapfram 中内核的相关参数，供下次trap的时候，uservec 使用
  p->trapframe->kernel_satp = r_satp();         // kernel page table
  p->trapframe->kernel_sp = p->kstack + PGSIZE; // process's kernel stack
  p->trapframe->kernel_trap = (uint64)usertrap;
  p->trapframe->kernel_hartid = r_tp();         // hartid for cpuid()

  // set up the registers that trampoline.S's sret will use
  // to get to user space.
  
  // set S Previous Privilege mode to User.
  // 设置寄存器 sstatus
  unsigned long x = r_sstatus();
  // 设置用户特权级别
  x &= ~SSTATUS_SPP; // clear SPP to 0 for user mode
  // 恢复进入到监督模式之前中断开/关状态
  x |= SSTATUS_SPIE; // enable interrupts in user mode
  w_sstatus(x);

  // set S Exception Program Counter to the saved user pc.
  // 设置 寄存器 sepc 的值， 在sret 的时候，sepc 会赋值给寄存器 pc
  w_sepc(p->trapframe->epc);

  // tell trampoline.S the user page table to switch to.
  // 获取到用户态的page table
  uint64 satp = MAKE_SATP(p->pagetable);

  // jump to userret in trampoline.S at the top of memory, which 
  // switches to the user page table, restores user registers,
  // and switches to user mode with sret.
  // 调用 userret 从内核态切换到用户态
  uint64 trampoline_userret = TRAMPOLINE + (userret - trampoline);
  ((void (*)(uint64))trampoline_userret)(satp); // satp 存储到寄存器a0中
}

usertrapret 的处理流程大致如下：

  • 设置寄存器 stvec, 指向 kernel/trampoline.S 中的 uservec，形成完美闭环。
  • 设置 uservec 需要使用的内核相关数据，即填充结构体 trapframe，供下次 trap 使用。
  • 设置寄存器 SEPC，指向 ecall 的下一条指令。
  • 获取到用户态的 page table
  • 执行 kernel/trampoline.S 中的 userret 函数，用户态 page table 的地址作为参数。
userret

userret 的逻辑和 uservec 的逻辑正好相反：

  • 切换页表，从内核态 page table 切换到 用户态 page table。
  • 恢复用户态函数的执行状态（通过读取 trapframe 结构体来恢复各个寄存器的值)。
  • 调用 sret 指令，跳转到用户态， 会把寄存器 sepc 的值（从上述可知是 ecall 的下一条指令）就会加载到寄存器 pc，让用户态函数继续执行。

        sfence.vma zero, zero
        csrw satp, a0
        sfence.vma zero, zero

        # restore all but a0 from TRAPFRAME
        ld ra, 40(a0)
        ld sp, 48(a0)
        ld gp, 56(a0)
        ld tp, 64(a0)
        ld t0, 72(a0)
        ld t1, 80(a0)
        ld t2, 88(a0)
        ld s0, 96(a0)
        ld s1, 104(a0)
        ld a1, 120(a0)
        ld a2, 128(a0)
        ld a3, 136(a0)
        ld a4, 144(a0)
        ld a5, 152(a0)
        ld a6, 160(a0)
        ld a7, 168(a0)
        ld s2, 176(a0)
        ld s3, 184(a0)
        ld s4, 192(a0)
        ld s5, 200(a0)
        ld s6, 208(a0)
        ld s7, 216(a0)
        ld s8, 224(a0)

xv6 内核态触发 trap 处理流程

kernelvec

内核态 trap 的处理要比用户态trap的处理简单的多，先存储寄存器，然后调用 kerneltrap 处理逻辑，最后恢复寄存器：

        #
        # interrupts and exceptions while in supervisor
        # mode come here.
        #
        # the current stack is a kernel stack.
        # push registers, call kerneltrap().
        # when kerneltrap() returns, restore registers, return.
        #
.globl kerneltrap
.globl kernelvec
.align 4
kernelvec:
        # make room to save registers.
        addi sp, sp, -256

        # save caller-saved registers.
        sd ra, 0(sp)
        sd sp, 8(sp)
        sd gp, 16(sp)
        sd tp, 24(sp)
        sd t0, 32(sp)
        sd t1, 40(sp)
        sd t2, 48(sp)
        sd a0, 72(sp)
        sd a1, 80(sp)
        sd a2, 88(sp)
        sd a3, 96(sp)
        sd a4, 104(sp)
        sd a5, 112(sp)
        sd a6, 120(sp)
        sd a7, 128(sp)
        sd t3, 216(sp)
        sd t4, 224(sp)
        sd t5, 232(sp)
        sd t6, 240(sp)

        # call the C trap handler in trap.c
        call kerneltrap

        # restore registers.
        ld ra, 0(sp)
        ld sp, 8(sp)
        ld gp, 16(sp)
        # not tp (contains hartid), in case we moved CPUs
        ld t0, 32(sp)
        ld t1, 40(sp)
        ld t2, 48(sp)
        ld a0, 72(sp)
        ld a1, 80(sp)
        ld a2, 88(sp)
        ld a3, 96(sp)
        ld a4, 104(sp)
        ld a5, 112(sp)
        ld a6, 120(sp)
        ld a7, 128(sp)
        ld t3, 216(sp)
        ld t4, 224(sp)
        ld t5, 232(sp)
        ld t6, 240(sp)

        addi sp, sp, 256

        # return to whatever we were doing in the kernel.
        sret
kerneltrap

kerneltrap 的处理也比较简单：

  • 保存 spec， sstatus 寄存器，应对进程切换的状况。
  • 在进入到监督模式之前的特权级别必须是监督模式，否则panic。
  • 中断必须禁用，否则panic。
  • 对于未知的 trap 直接 panic。
  • 对于时钟中断，调用 yield 进行进程切换。
  • 寄存器 spec，sstatus 复位。
// interrupts and exceptions from kernel code go here via kernelvec,
// on whatever the current kernel stack is.
void 
kerneltrap()
{
  int which_dev = 0;
  uint64 sepc = r_sepc();
  uint64 sstatus = r_sstatus();
  uint64 scause = r_scause();
  
  if((sstatus & SSTATUS_SPP) == 0)
    panic("kerneltrap: not from supervisor mode");
  if(intr_get() != 0)
    panic("kerneltrap: interrupts enabled");

  if((which_dev = devintr()) == 0){
    // interrupt or trap from an unknown source
    printf("scause=0x%lx sepc=0x%lx stval=0x%lx\n", scause, r_sepc(), r_stval());
    panic("kerneltrap");
  }

  // give up the CPU if this is a timer interrupt.
  if(which_dev == 2 && myproc() != 0)
    yield();

  // the yield() may have caused some traps to occur,
  // so restore trap registers for use by kernelvec.S's sepc instruction.
  w_sepc(sepc);
  w_sstatus(sstatus);
}

进程调度

xv6 进程间切换发生在如下两种情况：

  • 系统中断， 比如 time interrupt， 会调用 yield 进行切换。
  • 调用 xv6 的 sleep 和 wakeup 。

寄存器

寄存器 描述
x0/zero 始终为0
ra 保存 return address
sp 保存栈顶地址

yield 和 sched

sched 切换到 scheduler 的上下文，yield 修改进程状态： RUNNING -> RUNNABLE ,并调用 sched 切换到 scheduler。

void
sched(void)
{
  int intena;
  struct proc *p = myproc();

  if(!holding(&p->lock))
    panic("sched p->lock");
  if(mycpu()->noff != 1)
    panic("sched locks");
  if(p->state == RUNNING)
    panic("sched RUNNING");
  if(intr_get())
    panic("sched interruptible");

  intena = mycpu()->intena;
  swtch(&p->context, &mycpu()->context);
  mycpu()->intena = intena;
}

// Give up the CPU for one scheduling round.
void
yield(void)
{
  struct proc *p = myproc();
  acquire(&p->lock);
  p->state = RUNNABLE;
  sched();
  release(&p->lock);
}

scheduler 切换到 用户进程

在kernel/main.c 的 main 函数最后，会在每个 hart 执行进程的调度 scheduler：

void
main()
{
  //...
  scheduler();        
}

scheduler 其内部是一个死循环，其遍历 proc，寻找状态为 RNNABLE 的进程，通过调用 swtch 来进行进程切换， 如果没有合适的进程，则执行 wfi 指令进入到低功耗待机状态，等待中断的到来。

void
scheduler(void)
{
  struct proc *p;
  struct cpu *c = mycpu();
  c->proc = 0;
  for(;;){
    intr_on();

    int found = 0;
    for(p = proc; p < &proc[NPROC]; p++) {
      acquire(&p->lock);
      if(p->state == RUNNABLE) {
        p->state = RUNNING;
        c->proc = p;
        swtch(&c->context, &p->context);
        c->proc = 0;
        found = 1;
      }
      release(&p->lock);
    }
    if(found == 0) {
      intr_on();
      asm volatile("wfi");
    }
  }
}

在 scheduler 中最重要的两行代码：

        swtch(&c->context, &p->context);
        // Process is done running for now.
        // It should have changed its p->state before coming back.
        c->proc = 0;

如果单看注释，会云里雾里。从 swtch 的汇编代码中可以看出，并没有寄存器 pc 的变更，但是需要注意的是，在 allocproc 这个函数里面有如下代码：

  p->context.ra = (uint64)forkret;
  p->context.sp = p->kstack + PGSIZE;

在 调用 swtch 的时候， forkret 的地址会写入寄存器 ra， 当 swtch 返回的时候，ra 的值会写入到寄存器 pc，所以会从 forkret 开始执行。最终会调用 prepare_return ：

void
prepare_return(void)
{
  // ...
  // set S Exception Program Counter to the saved user pc.
  w_sepc(p->trapframe->epc);
}

最终会切换到用户进程执行。

sleep 和 wake

sleep 调用 sched 出让 cpu， wake 修改下进程的状态：SLEEPING -> RUNNABLE：

void
sleep(void *chan, struct spinlock *lk)
{
  struct proc *p = myproc();
  
  acquire(&p->lock);
  release(lk);

  p->chan = chan;
  p->state = SLEEPING;

  sched();

  p->chan = 0;

  release(&p->lock);
  acquire(lk);
}

void
wakeup(void *chan)
{
  struct proc *p;

  for(p = proc; p < &proc[NPROC]; p++) {
    if(p != myproc()){
      acquire(&p->lock);
      if(p->state == SLEEPING && p->chan == chan) {
        p->state = RUNNABLE;
      }
      release(&p->lock);
    }
  }
}
