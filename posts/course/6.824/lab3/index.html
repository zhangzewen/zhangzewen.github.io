Tips

  • 选举时间间隔和心跳间隔，根据在 lab3 的描述文档中的 hints，可选心跳间隔为 100ms，选举间隔可以在 [300ms, 600ms] 这个区间随机。

  • 详细阅读其提供的 Raft Structure Advice ，特别是：

    A Raft instance has two time-driven activities: the leader must send heart-beats, and others must start an election if too much time has passed since hearing from the leader. It’s probably best to drive each of these activities with a dedicated long-running goroutine, rather than combining multiple activities into a single goroutine.

    其意思是说对于节点的每个角色都有自己的goroutine，不建议在一个goroutine内使用一个死循环加有限状态机来实现，如：

    for {
  rf.mu.Lock()
  role := rf.role
  rf.mu.Unlock()
  switch role {
  case Leader:
    // ...
    break
  case Follower:
    // ...
    break
  case Candidate:
    // ...
    break
  }
}

    这样写的话，需要额外维护触发状态切换的管道或条件变量之类，徒增繁琐。

  • 仔细阅读 Student‘s Guide to Raft 和 Instructors’ Guide to Raft 。

  • 确认在当前任期下发送 RPC 请求 和 处理 RPC 响应，即每次处理的时候都需要判断当前节点的角色和任期，例如在发送 RPC 请求的时候：

    // ...
rf.mu.Lock()
if rf.role != Leader/*Follower/Candidate*/ {
	rf.mu.Unlock()
	return
}
// currentRoundTerm ，角色转换时候的Term
if rf.currentTerm != currentRoundTerm {
	rf.mu.Unlock()
	return
}
go rf.sendRequestVote(/*args*/)
// ...

    在处理 RPC 响应的时候

    // ...
successed := rf.peers[peer].Call(/**/)
if successed {
	rf.mu.Lock()
	if rf.role != Leader/*Follower/Candidate*/ {
		rf.mu.Unlock()
		return
	}
  // currentRoundTerm ，角色转换时候的Term
	if rf.currentTerm != currentRoundTerm {
		rf.mu.Unlock()
		return
	}
// ...

Part4： Snapshot

随着系统的持续运行，必定会伴随着日志容量逐渐庞大的过程，必定会导致：

  • 节点重启时导致 “重放” 日志变得越来越慢。
  • 节点状态落盘也会变得越来越慢。

Snapshot（即快照） 就是来解决此问题，lab 提供了如下接口：

Snapshot(index int, snapshot []byte)

其中的 index 是快照的时间点，在本 lab 中 是 logs 的下标，snapshot 是上层应用所做的快照，这个快照你可以理解为对包括 index 以及之前的日志进行压缩日志压缩，所以这个 snapshot 不需要考虑是怎么生成的，只需要要在修改 Part 3 的相关代码对其进行状态保存。 另外，InstallSnapshot 这个rpc 的调用和处理逻辑是和 AppendEntries 是相通的。 至此，这个部分的问题就演变为一个循环数组的问题。

还有就是何时调用 InstallSnapshot，在课件中给出了答案：

problem: what if follower’s log ends before leader’s log starts?

because follower was offline and leader discarded early part of log nextIndex[i] will back up to start of leader’s log so leader can’t repair that follower with AppendEntries RPCs thus the InstallSnapshot RPC
